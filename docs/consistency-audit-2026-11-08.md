# 数据一致性与宕机安全审计（2026-11-08，main 0453aad 之后）

## 方法

- **逐环节代码审计**：对 4 个环节做只读审计，每条风险要求给出 file:line、具体触发步骤和后果，并区分"已确认"与"推测"。4 个环节是：
  - 入口：收单 → Kafka → Raft；
  - 撮合：撮合、快照与恢复；
  - 发布：outbox → Kafka → 推送；
  - 落库：MySQL 投影。

  报告里标为"已确认"的，最严重的几条（O1、R1/E2、R2、R3）已由主会话对照源码复核。
- **形式化模型检查**：[`scripts/model/projection_model.py`](../scripts/model/projection_model.py) 对 MySQL 投影协议做显式状态穷举，覆盖：
  - 两个消费者的任意交错；
  - 任意批次切分；
  - MySQL 提交后、位点提交前宕机导致的重发；
  - 转交标记丢失，以及每个场景最多 2 次宕机。

  建模的前提有三条，没有放进模型里检查：
  - 单个事务在 REPEATABLE READ 加锁读下可串行化；
  - 重发发生在去重窗口内；
  - 同一订单的事件都在同一个 Kafka 分区内、保持顺序。

## 结论一览

| # | 环节 | 问题 | 后果 | 严重度 |
|---|---|---|---|---|
| **E1** | 撮合 | 去重状态不属于复制状态：引擎的 `seen_command_ids` 只增不减，重启后只从挂单重建；Raft 层只保留 100 万个 ID 的窗口，重启后从未压缩的日志重建 | 迟到的重复指令在没重启过的节点上被拒、在重启过的节点上被再执行，**副本分叉、重复成交**；有成交证明时节点反复崩溃重启；同时内存无限增长 | **高** |
| **R1** | 发布 | outbox 发布进度按"文件名 + 字节偏移"在副本间共享，但安装过 Raft 快照的节点 outbox 内容不同 | 换 leader 后跳过一段从未发出的成交，**成交事件永久丢失** | **高** |
| **E2** | 撮合 | 强平的批量撤单按 HashMap 顺序发出 | 成交证明在重放时不一致，节点崩溃；各副本的事件编号对不上 | **高** |
| **E3** | 撮合 | 日志压缩时，快照编号和快照内容分两次读取，中间可能被后台写线程换掉 | 存进去的快照"标签和内容不符"，节点重启时崩溃，需要人工修复 | 高（可用性） |
| **O1** | 落库 | 改单投影把引擎的"新剩余量"当成总量写进 `qty`，还写入 MODIFY_PENDING；引擎拒绝改单时也不回滚 | 状态错成 FILLED、永久卡在 MODIFY_PENDING、成交量少记（**模型已复现**） | **高** |
| **I1** | 入口 | 撮合消费者解不开的消息（比如改了路由版本）只写一条日志就跳过 | 已回复客户端"受理"的订单**丢失** | 高（发生在路由变更时） |
| **I2** | 入口 | 指令 ID 由客户端给出、全局唯一但不校验；ID 冲突的指令被 Raft 层静默丢掉 | 已受理的订单或撤单丢失，客户端收不到任何拒绝报告 | 高（取决于 ID 怎么发放） |
| **R2/R3** | 发布 | 品种迁移不检查源组的 outbox 是否发完；投影按 raft_index 选"最新事件"，不区分组 | 迁移后新旧两组的事件交叉到达，订单状态倒退 | 高（启用迁移时） |
| I3 | 入口 | 节点卸任 leader 后，迟到的请求留在 pending 队列，下次当选时被提交 | 和 E1 叠加时，重复执行或顺序错乱 | 中 |
| I4 | 入口 | 5000 笔一批的 WS 请求部分写 Kafka 失败，整批回复失败，已写入的那部分照样撮合 | 客户端以为被拒的订单仍然成交 | 中 |
| O2 | 落库 | 执行投影的死信提交把位点推过了还没落库的记录 | 毒消息 + 宕机时，成交事件丢失 | 中 |
| O3 | 落库 | 隔离级别依赖服务器默认的 REPEATABLE READ，代码里没写死 | 服务器配成 RC 时，成交被标成已处理却没加到订单上 | 中 |
| O4 | 落库 | 超过 24 小时窗口的重发（比如消费组位点丢失后从头消费）会被再加一次 | `filled_qty` 和 `filled_notional` 重复累加；`order_fills` 不受影响 | 中 |
| P1 | 推送 | user-stream 实际是"最多一次"：断线或重启期间的事件永远补不回来 | 用户漏收 FILLED 推送，只能靠查询接口对账 | 中 |
| P2 | 推送 | 推送的 `event_id` 不含订单号，自成交时 taker 和 maker 两条推送的 ID 相同 | 客户端按 ID 去重会丢掉其中一条 | 中 |
| — | 其他 | 不忽略 seek 失败；开启 `enable.gapless.guarantee`；MySQL 时钟回拨时环形分区可能清掉当前小时（今天新代码引入）；证明文件残尾不截断；改分区数和回滚 | 详见各环节报告 | 低–中 |

## 已验证成立的保证

- 引擎只在指令进入撮合后才回复确认，Kafka 位点也只在转发成功后才提交。同一品种的指令从头到尾保持顺序。
- WAL 恢复做三件事：校验每条记录、截掉写坏的尾部、拒绝编号空洞。恢复时跳过快照已经覆盖的日志，之后的日志按成交证明逐条核对。
- 快照写入是原子的：先写临时文件，fsync，rename，再 fsync 目录。后台快照（今天的改动）与原来的导出方式**完全等价**，快照里也没有遗漏影响撮合的状态，去重状态除外（见 E1）。
- outbox 有三条保证：
  - 写入后、刷盘前宕机，不丢也不重；
  - Kafka 已确认、发布进度还没写盘时宕机，只会重发，不会跳过；
  - 只删除已经封存的段文件。
- MySQL 投影由模型验证。在上述前提下，宕机、重发和标记丢失的任意组合都满足：每笔成交恰好计入一次，最终状态正确。今天加的"合并转交"同样经过验证，不会让事件永久滞留。

## 修复优先级

1. **E1**：把去重改成复制状态的一部分。用一个按 raft_index 淘汰的有界窗口，存进快照，所有副本据此做出相同决定。这样内存也有了上限。
2. **R1**：outbox 的发布进度改用逻辑位置 `(raft_index, ordinal)`，不再用字节偏移。
3. **E2、E3**：撤单先按时间排序；快照编号从实际存入的那份字节里读。
4. **O1**：改单投影改由成交事件 MODIFIED 驱动，`qty` 等于"改单时已成交量 + 剩余量"；指令线程不再改订单行。
5. **I1、O2、I3、I4**：解不开的指令进死信队列而不是丢弃；死信提交不越过当前批次；卸任后清空 pending；部分失败时回复逐条结果。
6. **R2/R3**：迁移前要求源组 outbox 发完；投影的状态改成终态不可回退。
7. 其余低风险项按顺序处理。
